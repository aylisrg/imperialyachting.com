# Передача email из раздела Docs (`/documents`) в PMS

**Тип:** интеграция · **Приоритет:** P1 (High) · **Оценка:** 1,5–4 дня (зависит от PMS, см. ниже)
**Блокеры:** ответы владельца (раздел 3); вход по magic link на `/documents` должен быть в main.
**PMS:** `<НАЗВАНИЕ PMS — заполнит владелец>` · **API-документация:** `<ссылка>`

## 1. Зачем
Каждый, кто запросил документы компании (License, EJARI, реквизиты), — тёплый лид или
партнёр: брокер, агент, корпоративный клиент. Сейчас эти контакты оседают в Supabase и
видны только на `/admin/documents`. Цель: **каждый подтверждённый email автоматически
попадает в PMS** с источником «Website Docs», без дублей и без ручного переноса, чтобы
менеджер мог с ним работать в привычной системе.

## 2. Что уже сделано на сайте (параллельная задача)
- `/documents` открыта для всех; скачивание PDF и реквизиты доступны после входа по
  magic link (email обязателен, имя и компания по желанию; ссылка живёт 24 ч, cookie — 30 дней).
- Supabase, таблица `document_contacts`: одна строка на email (уникальный, в нижнем регистре),
  статистика (`verified_at`, `last_login_at`, `login_count`, `download_count`, `last_country`, …)
  и поля outbox для PMS: `pms_sync_status` (`pending` | `synced` | `failed` | `skipped`, по умолчанию
  `pending`), `pms_synced_at`, `pms_external_id`, `pms_last_error`, `pms_attempts`.
- Supabase, таблица `document_access_events`: журнал `link_requested` / `login` / `download`
  (с `document_slug`).
- Временный адаптер `src/lib/pms/contacts.ts`: после подтверждённого входа, если задан
  `PMS_CONTACTS_WEBHOOK_URL`, шлёт POST (заголовок `Authorization: Bearer ${PMS_CONTACTS_WEBHOOK_TOKEN}`,
  если токен задан, и `Idempotency-Key = contact.id`) и записывает `synced`/`failed`, `pms_attempts`,
  `pms_last_error`. Вызов идёт через `after()` после редиректа, таймаут 8 с — вход не тормозит.
  Если env не задан, строки остаются `pending`: ничего не теряется, всё можно дозалить бэкфиллом.
- Контракт (событие `docs_contact.verified`):
  ```json
  { "event": "docs_contact.verified", "occurredAt": "<ISO>", "source": "imperialyachting.com/documents",
    "contact": { "email": "jane@acme.com", "name": "Jane Doe", "company": "Acme Ltd", "country": "AE",
      "firstSeenAt": "<ISO>", "verifiedAt": "<ISO>", "lastLoginAt": "<ISO>",
      "loginCount": 1, "downloadCount": 0 } }
  ```
- Уведомления команде (Telegram и письмо админу) уже работают, на каждый подтверждённый вход.
  В админке `/admin/documents` есть список контактов со статусом синхронизации.

## 4. Объём работ
1. **Секреты и конфиг.** Env в Vercel: `PMS_CONTACTS_WEBHOOK_URL` и `PMS_CONTACTS_WEBHOOK_TOKEN` (вариант вебхука)
   или `PMS_API_BASE_URL` и `PMS_API_KEY` (вариант API). Production указывает на боевую PMS,
   Preview — на sandbox или отключён. Без префикса `NEXT_PUBLIC_`, значения не логировать.
2. **Адаптер** `src/lib/pms/contacts.ts`. Интерфейс сохраняем: `syncContactToPms(contact) → { status, externalId?, error? }`.
   - Вебхук (b или c): включить env; при необходимости поправить payload под сценарий.
   - Прямой API (a): upsert по email (поиск, затем create или update), маппинг по таблице, тег и источник,
     сохранить `pms_external_id`; при следующих синхронизациях обновлять запись по нему. `Idempotency-Key`
     уже передаётся.
   - Вызов уже не блокирует вход (`after()`, таймаут 8 с) — сохранить это при замене адаптера.
3. **Ошибки и ретраи.** Сетевые ошибки, 5xx, 408 и 429 повторяем; остальные 4xx не повторяем.
   Уже есть: при неудаче `pms_attempts += 1`, `pms_last_error` (код, до 500 символов, без токенов),
   статус `failed`. Добавить классификацию повторяемых ошибок. После 5 неудач — одно оповещение в Telegram, дальше только ручной повтор.
   Исключённые адреса и отозванное согласие получают статус `skipped`.
4. **Бэкфилл и повторы.** Роут `/api/cron/pms-sync` с авторизацией `verifyBearer` по `CRON_SECRET`,
   как в `src/app/api/cron/expire-holds/route.ts`. Он берёт `verified_at is not null and pms_sync_status in
   ('pending','failed') and pms_attempts < 5`, сначала старые, пачками по 50. Добавить роут в `vercel.json`.
   На тарифе Hobby Vercel Cron запускается раз в сутки, поэтому нужен fallback в `.github/workflows/booking-cron.yml`
   (каждые 15 мин) или ручная кнопка. Плюс скрипт `scripts/pms-backfill.ts` с `--dry-run` для первичной заливки.
5. **Повторная активность** (по ответу владельца): при повторном входе или скачивании ставить контакт
   обратно в `pending` (обновление, не создание) или отправлять отдельное событие `docs_contact.activity`.
6. **Админка `/admin/documents`.** Фильтр по статусу и счётчики (pending / synced / failed / skipped), текст ошибки
   во всплывающей подсказке, ссылка на карточку в PMS (если есть шаблон URL), кнопки «Отправить повторно» (по строке)
   и «Синхронизировать все pending/failed».
7. **Согласие.** Заменить черновик под формой (`src/components/documents/DocumentsAccessForm.tsx`) утверждённым текстом. Если нужна галочка на маркетинг — миграция
   (`marketing_consent boolean`, `consent_at timestamptz`) и передача этих полей в PMS.
8. **Тесты и документация.** Vitest: маппинг, upsert без дублей, классификация ошибок, 401 у cron без секрета,
   выборка бэкфилла. В `DOCUMENTS_RU.md` добавить раздел «PMS»: env, повтор, бэкфилл.

## 5. Критерии приёмки
- [ ] Новый email после клика по magic link появляется в PMS **не позже чем через 1 мин** с правильными именем,
      компанией, страной, тегом и источником `Website Docs`. Строка получает `synced`, `pms_synced_at` и `pms_external_id`.
- [ ] Повторный вход, тот же email в другом регистре (`Jane@Acme.com`) и контакт, заранее созданный в PMS вручную,
      **не создают дубль**: запись обновляется или связывается.
- [ ] Email, который только запросил ссылку и не подтвердил её, в PMS **не попадает**.
- [ ] Сбой PMS (таймаут, 500, неверный токен) **не ломает** вход и скачивание, время ответа входа не растёт.
      Строка получает `failed`, текст ошибки в `pms_last_error`, `pms_attempts` увеличен; следующий запуск cron повторяет попытку.
- [ ] Без env PMS строки остаются `pending`, в логах нет ошибок.
- [ ] Бэкфилл переносит **все** подтверждённые `pending`/`failed`; повторный запуск не создаёт дублей; `--dry-run` ничего не отправляет.
- [ ] В админке видны статус и ошибка; «Отправить повторно» работает; `/api/cron/pms-sync` без секрета отвечает 401.
- [ ] Секретов нет в клиентском бандле и в логах. `npm run lint`, `npm test` и `npm run build` зелёные; приёмка на sandbox пройдена.

## 6. Вне скоупа
- Обратная синхронизация из PMS на сайт (статусы, удаления, отписки) — отдельная задача.
- Перенос в PMS других лидов сайта (бронирования, контактная форма, продажи яхт). Адаптер делаем переиспользуемым.
- Email-рассылки по этим контактам; изменения самого magic-link входа.
- Автоматическое удаление из PMS по запросу субъекта данных. Пока это ручная процедура, её описываем в `DOCUMENTS_RU.md`.

## 7. Риски
- **У PMS нет API или вебхука.** Plan B: кнопка «Экспорт CSV» в `/admin/documents` (+0,5 дня) и ручной импорт.
- **OAuth2 с истекающими токенами.** Нужно хранить и обновлять refresh token: +1 день.
- **Дубли с уже существующими контактами в PMS.** Нужен поиск по email до создания; согласовать правила слияния.
- **Лимиты API PMS.** Бэкфилл идёт пачками с паузой, 429 повторяется.
- **Правовые требования (PDPL/GDPR) при передаче в PMS за пределами ОАЭ.** Без утверждённого текста согласия в прод не включаем.
- **Cron раз в сутки на тарифе Hobby.** Ретраи задерживаются, поэтому нужен fallback через GitHub Actions.

## 8. Оценка (без учёта ожидания ответов владельца)
| Вариант | Дни |
|---|---|
| Вебхук PMS или Zapier/Make/n8n (сценарий на стороне владельца) | 1,5 |
| Прямой REST API, ключ API, upsert по email | 2,5–3 |
| Прямой API с OAuth2 и/или контакт + компания + активности | 3,5–4 |

Допущения: magic-link уже в main; у PMS есть документированный API и sandbox; ответы на раздел 3 придут одним пакетом.

## 9. Приоритет
**P1.** Данные не теряются (копятся в `pending`), но каждый день без синхронизации — это лиды вне рабочей системы
менеджеров. Брать сразу после мержа magic-link и получения ответов из раздела 3.
